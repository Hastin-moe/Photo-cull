# GUI 设计方向（供设计团队协作）

最后更新：2026-10-23　适用版本：1.6（前后端分离之后）

这份文档给后续参与界面设计的团队一个共同起点：现在的界面是什么样、哪些地方要改、往哪个方向改、技术上有哪些约束。具体视觉方案由设计团队提出，这里只给大的方向和边界。

---

## 1. 现状

| 页面 | 文件 | 结构 |
|---|---|---|
| 照片筛选 | `web/cull/` | 左侧设置栏（文件夹、筛选方式、AI、输出、整理、高级参数）＋右侧工作区（空状态 → 三段进度 → 统计＋内嵌报告） |
| 筛选报告 | `web/report/` | 独立 HTML（会被拷走、双击打开）：统计、筛选条、缩略图网格、星级、删除 |
| 照片编辑 | `web/edit/` | 三栏：文件列表／预览／调整面板（监看、基本、暗角、曲线、LUT、导出） |
| 启动提示 | `web/help.html` | 另一个程序没开时的提示页 |

共用：`web/common/tokens.css`（颜色、字体、圆角、阴影变量，含深色模式）、`web/common/i18n.js`（三语）。

**主要问题**

1. **设置堆在一起**：筛选页左栏一次摊开 20 多个选项，新用户不知道从哪开始；「演练模式」「整理输出」这类重要概念只靠一行小字说明。
2. **流程看不见**：实际流程是「选文件夹 → 本地分析 → AI 细评 → 复核 → 写入／整理」，界面上只有三个进度条，复核和整理被压在报告 iframe 里。
3. **复核效率低**：报告是网格＋鼠标点星，没有大图浏览、键盘打分、连拍组对比，挑片时要来回放大。
4. **编辑区底色偏暖**：现在的背景 `#f4f3ef` 带暖色，会影响对照片颜色的判断。
5. **两个程序观感不统一**：头部、按钮、分段控件各写一份，细节不一致。
6. **多语言下的排版**：英文、日文比中文长 30%–60%，已出现按钮换行、窄标签竖排（已临时修复）；固定宽度的地方都要改成自适应。
7. **几乎没有图标和插图**：全靠文字，扫读慢。

## 2. 设计原则

1. **照片优先**：界面退到后面。照片周围只用中性灰，不用有色背景、彩色装饰；状态色（绿／黄／红）只用于和 Lightroom 色标对应的地方。
2. **安全感要看得见**：本工具的核心承诺是「不改原片、删除可恢复、默认复制」。界面要在关键操作前明确告知（写入哪些文件、删除去哪里、是否会搬动文件），而不是藏在说明文字里。
3. **渐进展开**：默认只露出完成一次筛选所需的最少选项；高级参数、AI 模型细节、整理规则按需展开。
4. **键盘优先的复核**：挑片是高频重复动作，要能完全不碰鼠标完成（参考 Photo Mechanic、Lightroom 的习惯：数字键打星、X 拒绝、方向键切换）。
5. **三种语言都是一等公民**：设计稿至少出中、英、日三版截图；不用固定宽度承载文字。
6. **本地、离线、可信**：不引入需要联网才能显示的资源（字体、图标都随工具发布），不做账号、不做埋点。

## 3. 大的方向

### 3.1 图形引导（重点）

把流程本身画出来，让用户一眼知道「我在哪一步、下一步做什么、会发生什么」。

- **首次使用向导**（3 步）：选照片文件夹 → 选方式（仅本地／加 AI，配一句费用说明）→ 建议先演练。完成后直接开始，之后不再弹出（可在设置里重看）。
- **流程条**：页面顶部用横向步骤条代替现在的三个进度卡片：
  `① 分析 → ② AI 细评（可跳过）→ ③ 复核 → ④ 写入／整理`
  每一步显示状态（等待／进行中／完成／跳过）和关键数字。
- **漏斗图**：完成后用一张小漏斗展示「总数 120 → 入围 64 → 4★以上 18 → 淘汰 21」，比一排统计数字更直观，点击某一层直接筛选到对应照片。
- **关键操作前的预览**：
  - AI 细评前：张数、预计费用区间、用哪家模型（已有弹窗，改成更清楚的卡片）。
  - 写入前：会改哪些文件（RAW 边车／JPEG 内嵌），配一个「这不会改动画面数据」的说明图标。
  - 整理前：用文件夹树预览结果（现在只有两行文字示例），移动模式用醒目的警示样式。
- **空状态与插图**：空文件夹、没有入围、AI 全部失败等状态各有一张简单插图和一句「下一步做什么」。
- **就地提示（coach marks）**：第一次看到「RAW＋JPEG 配对」「连拍组」「拒绝」时出现一次性小提示，之后不再打扰。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 照片筛选     ① 分析 ✓ ── ② AI 细评 ●64/64 ── ③ 复核 ── ④ 写入/整理      │
├──────────────┬───────────────────────────────────────────────────────┤
│ 文件夹        │   120 ▸ 入围 64 ▸ 4★+ 18        淘汰 21               │
│ 方式 本地+AI  │  ┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐                  │
│ (更多设置 ▾)  │  │    ││    ││    ││    ││    ││    │  ← 网格／大图切换  │
│              │  └────┘└────┘└────┘└────┘└────┘└────┘                  │
│ [开始筛选]    │  1–5 打星  X 拒绝  ←→ 切换  空格 大图                   │
└──────────────┴───────────────────────────────────────────────────────┘
```

### 3.2 复核体验

- 把报告从 iframe 改成照片筛选里的原生视图（独立的 `report.html` 保留，作为只读存档）。
- 三种视图：**网格**（快速扫）／**大图**（单张，带胶片条）／**对比**（连拍组 2–4 张并排，组内最佳有标记）。
- 连拍组默认折叠成一叠，只露最佳一张，展开看其他。
- 问题标记（模糊、过曝、闭眼…）用图标＋悬停说明，不再是红色文字串。
- AI 评语放在侧边抽屉：总分、五项分数的小条形图、评语、改进建议。
- 批量操作（删除所选、删除全部淘汰、整理）集中到一个底部操作条。

### 3.3 照片编辑

- **画布用中性灰**：预览区背景用中性 18% 灰（深色模式用接近黑的中性灰），面板也去掉暖色倾向。可以考虑编辑程序默认深色。
- 调整面板按 Lightroom 用户熟悉的顺序分组，每组可折叠、有图标；监看（直方图／波形）固定在顶部。
- **LUT 浏览器带缩略预览**：用当前照片渲染每个 LUT 的小图（后端已有渲染接口，可加一个小尺寸批量接口），替代纯文字列表；「我的 LUT」「内置」用标签切换。
- 镜头暗角选择器可以配一张示意图（四角渐暗的圆形），三档强度直观对比。
- 自动调整的结果（曝光、对比…）用一行可点击的「标签」显示，点一下回到该滑块。

### 3.4 统一外壳与设计系统

- 两个程序保留为两个进程（后端不变），但共用一套外壳：同样的头部、导航、语言切换、状态指示。
- 以后可以考虑一个总入口，在一个窗口里像 Lightroom 的模块一样切换「筛选／复核／编辑」。
- 设计系统落在 `web/common/`：
  - `tokens.css`：颜色（中性灰阶 10 级以上、状态色、焦点色）、字号阶梯、间距（4／8 倍数）、圆角、阴影、动效时长。浅色、深色两套。
  - 组件：按钮、分段控件、开关、滑块、输入框、下拉、卡片、弹窗、提示、步骤条、徽标、缩略图卡片。
  - 图标：选一套开源图标（如 Lucide、Phosphor，MIT 许可），以 SVG 放进 `web/common/icons/`，不走 CDN。

### 3.5 多语言排版要求

- 文字容器一律自适应宽度，按钮允许换行或缩写，不能截断成看不懂的样子。
- 英文按最长情况设计（通常比中文长 40%），日文注意长片假名词。
- 日文、中文不要混用字体：`tokens.css` 已按 `lang` 切换字体栈（中文优先苹方／微软雅黑，日文优先 Hiragino／游ゴシック）。
- 日文换行用 `line-break: strict`；不要把文字做进图片里。
- 数字、日期按语言格式化（前端已有 `fmtNum`）。

### 3.6 可访问性

- 文字与背景对比度达到 WCAG AA；状态不只靠颜色区分（星级＋图标＋文字）。
- 所有操作都能用键盘完成，有清晰的焦点样式；尊重 `prefers-reduced-motion`。

## 4. 技术约束（交接给设计和前端）

- **没有构建步骤**：现在是纯 HTML／CSS／JS，由 `gui.py` 直接提供，改完刷新浏览器即可看到。引入框架（React、Vue 等）前请先讨论；如果要用，倾向于轻量、可以直接以 ES 模块随工具发布的方案（如 Preact、Lit），保持「双击就能用、不需要 npm」。
- **所有文字走语言包**：HTML 写 `data-i18n="分组.键"`，脚本写 `T("分组.键", {变量})`，文字放 `locales/zh-CN.json`、`en.json`、`ja.json`；新增文字后运行 `python3 tools/check_i18n.py`。
- **颜色等只用 `tokens.css` 变量**，不在页面里写死。
- **报告页必须能单独打开**：`report.html` 生成时会把 `tokens.css`、`report.css`、`i18n.js`、`report.js` 和语言包内联进去，所以报告页不能依赖其他外部文件（图片用缩略图相对路径）。
- **接口**：界面通过 `/api/*` 和后端通信（请求头带 `X-Token`）。主要接口：

  | 程序 | 接口 | 作用 |
  |---|---|---|
  | 共用 | `POST /api/lang` | 切换语言 |
  | 共用 | `POST /api/choose` | 弹出系统的文件夹选择框 |
  | 筛选 | `GET /api/settings`、`POST /api/run`、`GET /api/status`、`POST /api/confirm`／`cancel` | 读设置、开始、轮询进度、确认 AI 调用 |
  | 筛选 | `POST /api/load`、`/api/mark`、`/api/trash`、`/api/organize`、`/api/reveal` | 载入上次结果、改星级、删除、整理、在文件管理器中显示 |
  | 编辑 | `GET /api/edit/state`、`POST /api/edit/list`、`/open`、`/render`、`/auto`、`/save` | 初始状态、文件列表、打开、渲染预览（返回 JPEG）、自动调整、保存 |
  | 编辑 | `POST /api/edit/library`、`/style`、`/lut_add`、`/lut_remove`、`/export`；`GET /api/edit/thumb`、`/export_status` | LUT 素材库、套用、添加／移除 LUT、导出 |

  做原型时可以直接连本地运行的程序；需要新接口（例如 LUT 缩略预览、批量缩略图）请在 Issue 里提出。

## 5. 分阶段建议

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 一：视觉整理 | 统一 tokens（中性灰阶、深色模式）、图标、按钮与表单组件；编辑区改中性灰；三语排版问题清零 | 只改 `web/` |
| 二：图形引导 | 首次向导、流程条、漏斗图、写入／整理前的预览、空状态插图 | 只改 `web/`，可能加 1–2 个查询接口 |
| 三：复核视图 | 原生复核视图（网格／大图／对比）、键盘打分、连拍折叠、AI 评语抽屉 | 前端为主，后端补批量缩略图接口 |
| 四：编辑增强 | LUT 缩略预览浏览器、面板分组与图标、HDR 显示模式的界面 | 后端加小尺寸批量渲染接口；HDR 与后端同步开发 |
| 五：统一外壳 | 一个入口切换筛选／复核／编辑 | 需要讨论进程结构 |

## 6. 希望设计团队交付

- 设计原则与视觉方向（2–3 个方案，含浅色／深色）。
- 组件库（对应 `tokens.css` 的变量命名），以及按钮、表单、弹窗等的全部状态（默认、悬停、按下、禁用、出错、加载中）。
- 关键流程的交互稿：首次使用、一次完整筛选、复核挑片、整理、编辑一张照片并导出。
- 每个页面的空状态、加载中、出错、部分失败状态。
- 中、英、日三种语言的关键页面截图，确认排版。

## 7. 待讨论的问题

1. 编辑程序是否默认深色？筛选程序是否跟随系统？
2. 是否在 1.x 就把报告改成原生视图，还是等复核视图整体完成再替换？
3. 是否需要一个总入口把两个程序合在一个窗口？
4. 图标和插图风格（线性／面性、是否手绘感），以及是否需要品牌标志。
5. 键盘快捷键是否与 Lightroom 完全一致，还是参考 Photo Mechanic？
